# 教学设计思想（Pedagogy）

> 适用对象：arcade->python 课程作者（设计 L3-L8 时参考）
> 来源：2026-09-04 L1/L2 设计讨论的沉淀
> 阅读时间：~10 分钟

## 为什么需要这份文档？

每次做新一节课（l3-*.md / l4-*.md...），你都会面对同一组问题：

- 这节课教什么？
- 几个练习？每个练习什么形式？
- 长项目做什么机制？
- 改错题改什么错？

**这份文档提供一套思考框架**，让你做设计时有方向，而不是凑数。

## 核心原则（5 条）

### 原则 1：教学点应该是 Python 语言本身，不是 API

| ✅ 教学点 | ❌ 不是教学点 |
|---|---|
| `score = score + 10`（Python 语法）| `info.change_score_by(10)`（API 调用） |
| `if score % 30 == 0:`（Python 语法）| 某个 MakeCode 块 |
| `each = total // people`（Python 语法）| 某个游戏机制 |

**为什么**：API 是工具，运算符/语法是语言骨架。骨架是通用的，工具每次都换。**学生学完你这一节课，能带着 Python 知识做别的项目，而不是只会在 MakeCode 里点 block**。

---

### 原则 2：场景驱动学习

**反例（知识点驱动）**：
> "今天我们学 `+`、`-`、`*`、`/`——这是运算符。"

**正例（场景驱动）**：
> "今天我们做一个超市收银系统。草莓3 元/个，汉堡8 元/个，你要算顾客买3 草莓+2 汉堡的总价。"

**学生角度**：场景让他**自然需要**运算符——他是为了"算总价"才用 `+` 和 `*`，不是"老师让我学运算符"。

**做练习前先问**：这个知识点**在哪个真实场景里学生会用到**？找不到场景 = 这个知识点**不该单独教**。

---

### 原则 3：改错必须是"真实错误"，不是"凑数的题"

**真实错误的标准**：

- ✅ 学生在**尝试理解 Python 行为**时会自然踩到的坑
- ✅ 这个错误**揭示了一条 Python 规则**
- ✅ 学生改完错误，**自然记住了这条规则**

**反例**：
- ❌ `\`写成 `/`——低级笔误，不揭示规则
- ❌ `=` 写成 `==`（如果 L2 没学过 `==`）——学生根本不知道

**经典真实错误例子**：

| 错误 | 揭示的 Python 规则 |
|---|---|
| `score = "小明"`（在算分的地方）| Python 区分数字和字符串 |
| `Score`（大写）| Python 区分大小写 |
| `info.change_score_by(score)`（score 未定义）| 必须先定义后使用 |
| `score = score * 1`（错写成 `*1`）| `*` 是乘，1 乘任何数是自己 |
| `money / people`（期望整数结果）| `/` 是真除法，`//` 才是整除 |
| `10 + 5 = 15`（条件用赋值而非比较）| `=` 是赋值，`==` 才是比较（**L3 学**）|

---

### 原则 4：练习和长项目形成"知识点三角"

```
前段  → 概念引入（这是什么、为什么用）
练习  → 显式化（学生犯错 → 发现 → 记住规则）
长项目 → 综合应用（把多个规则用起来）
```

**三者的角色**：

| 环节 | 角色 | 学生感受 |
|---|---|---|
| 前段 | 解释 | "哦，原来 Python 是这样" |
| 练习 | 暴露规则 | "啊，我犯了这样的错，Python 是这么工作的" |
| 长项目 | 串联规则 | "我会用了——把三个规则组合起来" |

**失败的常见模式**：练习和长项目**只重复前段内容**，没有"显式化"也没有"串联"——那练习和长项目就**没必要存在**。

---

### 原则 5：NPC 反馈替代机械判定

**反例**：
```python
# 学生在代码里写
total_price = 25

# 然后游戏显示 "answer: 25"   ← 冷冰冰
```

**正例**：
```python
# NPC 售货员在判定区里写
if total_price == 25:
    game.show_long_text("售货员：'对！总价25 元，找你0 元！'", 1)
else:
    game.show_long_text("售货员：'总价不对，再算算哦'", 1)
```

**为什么 NPC 反馈更好**：

- 学生**更投入场景**（"国王/售货员/收银员"比"answer" 生动）
- 判定代码**封装在 template 的 NPC 判定区**，学生修改区不涉及 if/else
- 学生**看 NPC 台词**，自然判断对错——不用老师讲

## 每节课的设计流程（4 步）

#### Step 1：确定知识点

问自己：**这节课教哪个 Python 概念？**

| 知识点 | 不属于本课 | 属于本课 |
|---|---|---|
| 变量定义/赋值/引用 | - | L1 ✅ |
| `+ - * / % **` 算术 | - | L2 ✅ |
| `== != > < >= <=` 比较 | L3 用 | - |
| `if / else` | - | L3 |
| `and or not` | - | L3 |
| `while` | - | L5 |
| `for` | - | L6 |

**明确**：本课**只教 1 个核心知识点**，不要贪多。

---

#### Step 2：找 1 个主场景（贯穿前段 + 长项目）

**主场景标准**：

- ✅ 学生能直觉理解（不需要背景知识）
- ✅ 自然需要本课知识点
- ✅ 和"星际冒险"游戏锚点能融合

**L1 主场景**：公主 + 星星 + 生命值/分数
**L2 主场景**：公主 + 金币 + 算分逻辑（金额运算）
**L3 主场景**：公主 + 多种条件（撞星加分、撞敌减血）

**找不到主场景 = 你教错了知识点，应该换一个。**

---

#### Step 3：设计 3 个练习（场景 + 真实错误 + Python 规则）

**每个练习的设计表**：

| 维度 | 问题 |
|---|---|
| 场景 | 学生要在什么情境下？ |
| 知识点 |揭示什么 Python 规则？ |
| 真实错误 |学生会怎么犯错？ |
| 形式 | 填空 / 改错 / 选择 / 拖拽 |
| NPC反馈 | 谁告诉学生"对了/错了"？ |

**3 个练习之间要互补**：

- 不能 3 个练习都改同一种错（重复）
- 不能 3 个练习都是填空（单调）
- 不能 3 个练习都覆盖同一个知识点（无效）

**典型组合**：

- 练习1：填空（巩固应用）
- 练习2：改错（揭示规则 A）
- 练习3：改错（揭示规则 B）

---

#### Step 4：设计长项目（综合应用 3 个练习的规则）

**长项目设计表**：

| 维度 | 描述 |
|---|---|
| 项目主题 | 在主场景上加什么新机制？ |
| 学生要做什么 | 8 个 step 左右，每步只做一件事 |
| 涉及本课知识点 | **所有 3 个练习覆盖的规则都用上** |
| 涉及之前学过的 | 巩固 L1-L{n-1} 的知识 |

**反例**：长项目只覆盖 1 个知识点——那这个长项目**只算练习的延伸**，不是真正的"综合应用"。

---

## 教学形式 vs 教学内涵

| 形式 | 何时用 | 何时不用 |
|---|---|---|
| 填空 | 学生已经知道"做什么"，但需要练习"怎么做" | 学生不知道概念——填空没意义 |
| 改错 | 有**真实错误**和**可显式化的 Python 规则**时 | 找不到真实错误——别硬凑 |
| 选择题 | 概念辨析（比如 `==` vs `=`） | 复杂计算场景 |
| 长项目 | 至少要综合 3 个规则时 | 只能综合 1 个规则——做成大练习 |

**原则**：形式服务内涵。**先确定内涵（场景/规则/NPC反馈），再选形式。**

## 学生修改区 vs NPC 判定区

每个练习的 .md 文件，分两个区：

```python
# =============================================
# ✏️ 学生修改区（不涉及 if/else 等本课未教内容）
# =============================================
strawberry_price = 3
burger_price = 8
strawberry_count = 3
burger_count = 2
total_price = ____   # ← 学生填
# =============================================

# =============================================
# 🔒 NPC 判定区（template 自动写好，可用 if/else）
# =============================================
if total_price == 25:
    game.show_long_text("售货员：'对！总价25 元'", 1)
else:
    game.show_long_text("售货员：'再算算哦'", 1)
# =============================================
```

**学生只看自己修改区**——NPC 判定区是 template 里固定的代码，学生**不需要读懂**，只看游戏反应。

**好处**：

- L2 没学 if/else，但 L2 练习能**用** if/else——判定区**封装了 if/else**
- L3 学会 if/else 后，可以回头看 NPC 判定区，理解"哦原来是这个原理"

## L1 已建立的"格式骨架"（后续沿用）

| 维度 | L1 经验 |
|---|---|
| step 标题格式 | `## {1. 欢迎 @showdialog}` 或 `## {2. 变量是什么？}` |
| 累积代码块 | `#### ~ tutorialhint`（不是普通 `~hint`） |
| python-template 块 | 放文件末尾，提供学生起步代码 |
| @showdialog 用法 | **只在纯讲解/回顾步骤**用，动手步骤不用 |
| hint 块 | **纯文本**，无 markdown 修饰、无 emoji、无行内代码 |
| 注释风格 | `# 标题`、`# ============` 分隔线、✏️ 一个就够了 |
| 变量命名 | snake_case（`myPlayer`、`info.set_life`） |
| SpriteKind | 小写（`SpriteKind.player`、`SpriteKind.food`） |
| 函数定义 | `def on_xxx(sprite, otherSprite):`（不用 `function`） |

## 决策记录（迭代历史）

### 2026-09-04 L2 设计讨论的 9 次迭代

| # | 用户反馈 | 学到的原则 |
|---|---|---|
| 1 | "教学点为什么是API" | 教学点应该是 Python，不是 API |
| 2 | "改错2、3 意义不明" | 改错不能硬凑，要有真实场景 |
| 3 | "用场景逻辑引导学生" | 场景驱动学习 |
| 4 | "练习3 改错意义在哪" | 改错必须是真实错误，不是凑数 |
| 5 | "练习1 改错不需要了" | 形式不重要，内涵重要 |
| 6 | "我说`**`是幂运算" | 沟通要明确术语 |
| 7 | "乘100 太干扰" | 场景数字要小、要聚焦 |
| 8 | "if/else 学生区不用，template 可以" | 判定代码可以封装 |
| 9 | "npc告诉对了错了" | 反馈要角色化，不用机械判定 |

### 教训

**形式先行的设计是陷阱**。

- ❌ "今天做3 个改错题"（先定形式）
- ✅ "今天教算术运算符，**找 3 个真实错误**让学生发现"（先定内涵）

**下次做 L3/L4/L5 时**：

1. 先问"教什么 Python 规则"
2. 找"什么场景需要这个规则"
3. 在场景里设计练习
4. 长项目把多个规则串起来
